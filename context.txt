## Project Identity

**Name:** Audit Log Service  
**Type:** Full-stack SaaS-style developer tool  
**Purpose:** A tamper-proof audit trail service any application can plug into via API. Every user action in a client app is logged, cryptographically chained, and verifiable. Tampering with any log entry breaks the chain and is mathematically detectable.  
**Target users:** Developers who need compliance-ready, immutable activity logs for their applications.  
**Real-world equivalents:** Papertrail, Datadog Audit Logs, AWS CloudTrail — but self-built.

## app.ts — Complete Express Setup

This is the entry point of the Express API. Middleware order is critical — wrong order breaks auth, CORS, or error handling.

```typescript
// src/app.ts

import express from 'express';
import helmet from 'helmet';
import cors from 'cors';
import morgan from 'morgan';
import rateLimit from 'express-rate-limit';

import eventsRouter from './routes/events';
import searchRouter from './routes/search';
import verifyRouter from './routes/verify';
import exportRouter from './routes/export';
import appsRouter from './routes/apps';
import healthRouter from './routes/health';
import { errorHandler } from './middleware/errorHandler';
import { apiKeyAuth } from './middleware/auth';
import logger from './config/logger';
import prisma from './config/db';
import redis from './config/redis';

const app = express();

// ─── Security middleware (must be first) ─────────────────────────────────────
app.use(helmet());  // Sets secure HTTP headers: X-Content-Type-Options, X-Frame-Options, etc.

// ─── CORS ─────────────────────────────────────────────────────────────────────
// Allows the Next.js dashboard (different domain) to call this API
app.use(cors({
  origin: [
    process.env.NEXTAUTH_URL || 'http://localhost:3001',  // Dashboard URL
    // Add any other allowed origins here
  ],
  methods: ['GET', 'POST', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true,
}));

// ─── Request parsing ──────────────────────────────────────────────────────────
app.use(express.json({ limit: '1mb' }));  // Limit prevents large payload attacks

// ─── HTTP request logging ─────────────────────────────────────────────────────
app.use(morgan('combined', {
  stream: { write: (message) => logger.info(message.trim()) },
  skip: (req) => req.path === '/health',  // Don't log health check spam
}));

// ─── Routes that do NOT require API key auth ──────────────────────────────────
app.use('/health', healthRouter);
app.use('/apps', appsRouter);  // Apps routes use NextAuth session auth, not API key

// ─── API key auth applied to all routes below this point ─────────────────────
app.use(apiKeyAuth);

// ─── Protected routes ─────────────────────────────────────────────────────────
app.use('/events', eventsRouter);    // POST /events — ingestion
app.use('/events', searchRouter);   // GET /events — search (same base path, different method)
app.use('/verify', verifyRouter);   // GET /verify — chain verification
app.use('/export', exportRouter);   // GET /export — CSV/JSON export

// ─── 404 handler ─────────────────────────────────────────────────────────────
app.use((req, res) => {
  res.status(404).json({
    success: false,
    error: { message: 'Route not found', code: 'NOT_FOUND', statusCode: 404 },
  });
});

// ─── Centralised error handler (must be LAST) ─────────────────────────────────
app.use(errorHandler);

// ─── Server startup ───────────────────────────────────────────────────────────
const PORT = parseInt(process.env.PORT || '3000');

const server = app.listen(PORT, () => {
  logger.info(`API server running on port ${PORT} in ${process.env.NODE_ENV} mode`);
});

// ─── Graceful shutdown ────────────────────────────────────────────────────────
// Railway and Docker send SIGTERM before killing the process
// This ensures in-flight requests complete before shutdown
async function shutdown(signal: string) {
  logger.info(`${signal} received — starting graceful shutdown`);

  server.close(async () => {
    logger.info('HTTP server closed — no new connections accepted');

    await prisma.$disconnect();
    logger.info('PostgreSQL disconnected');

    redis.disconnect();
    logger.info('Redis disconnected');

    logger.info('Graceful shutdown complete');
    process.exit(0);
  });

  // Force shutdown if graceful shutdown takes too long
  setTimeout(() => {
    logger.error('Graceful shutdown timeout — forcing exit');
    process.exit(1);
  }, 10000);
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));

export default app;  // Exported for Supertest in integration tests
```

**Why middleware order matters:**
1. `helmet()` first — sets security headers before anything else runs
2. `cors()` before routes — OPTIONS preflight requests must be handled before auth
3. `express.json()` before routes — body must be parsed before route handlers read it
4. `morgan` before routes — logs every incoming request including ones that fail auth
5. Public routes before `apiKeyAuth` — /health and /apps must work without API keys
6. `apiKeyAuth` middleware — all routes after this require valid API key
7. Protected routes — only reachable with valid API key
8. `errorHandler` last — catches errors thrown by any route or middleware above it

## Analytics Queries — Dashboard Stats

These queries power the StatsCards and charts on the main dashboard. They run on the server component — no client-side fetching.

```typescript
// Queries to add to a src/services/analyticsService.ts file

import prisma from '../config/db';

// Total event count for an app
export async function getTotalEventCount(appId: string): Promise<number> {
  return prisma.auditLog.count({ where: { appId } });
}

// Event volume per day for the last 30 days — powers the line chart
export async function getEventVolumeByDay(appId: string): Promise<{ date: string; count: number }[]> {
  const result = await prisma.$queryRaw<{ date: string; count: bigint }[]>`
    SELECT
      DATE(created_at) AS date,
      COUNT(*) AS count
    FROM audit_logs
    WHERE app_id = ${appId}
      AND created_at >= NOW() - INTERVAL '30 days'
    GROUP BY DATE(created_at)
    ORDER BY date ASC
  `;
  // BigInt to number conversion needed because PostgreSQL COUNT returns bigint
  return result.map(r => ({ date: r.date, count: Number(r.count) }));
}

// Top 10 actors by event count — "who is doing the most things?"
export async function getTopActors(appId: string): Promise<{ actorId: string; actorType: string; count: number }[]> {
  const result = await prisma.$queryRaw<{ actor_id: string; actor_type: string; count: bigint }[]>`
    SELECT
      actor_id,
      actor_type,
      COUNT(*) AS count
    FROM audit_logs
    WHERE app_id = ${appId}
      AND created_at >= NOW() - INTERVAL '7 days'
    GROUP BY actor_id, actor_type
    ORDER BY count DESC
    LIMIT 10
  `;
  return result.map(r => ({ actorId: r.actor_id, actorType: r.actor_type, count: Number(r.count) }));
}

// Action breakdown — "what types of events are most common?"
export async function getActionBreakdown(appId: string): Promise<{ action: string; count: number }[]> {
  const result = await prisma.$queryRaw<{ action: string; count: bigint }[]>`
    SELECT
      action,
      COUNT(*) AS count
    FROM audit_logs
    WHERE app_id = ${appId}
      AND created_at >= NOW() - INTERVAL '7 days'
    GROUP BY action
    ORDER BY count DESC
    LIMIT 20
  `;
  return result.map(r => ({ action: r.action, count: Number(r.count) }));
}

// Events in the last 24 hours — dashboard summary card
export async function getEventsLast24Hours(appId: string): Promise<number> {
  return prisma.auditLog.count({
    where: {
      appId,
      createdAt: { gte: new Date(Date.now() - 24 * 60 * 60 * 1000) },
    },
  });
}
```

**Note on `$queryRaw`:** Prisma's `$queryRaw` returns `bigint` for PostgreSQL `COUNT()` results. Always convert with `Number()` before returning to the frontend — JSON.stringify cannot serialise BigInt and will throw a runtime error.

### POST /apps/:id/rotate-key — Regenerate API key
```
Response 200:
{
  "success": true,
  "data": {
    "newApiKey": "clnewkey789..."   ← New key. Old key immediately stops working.
  }
}
```

**Why key rotation matters for the interview:** "What if an API key is leaked?" The rotate-key endpoint immediately replaces the key. The old key returns 401 on the next request. This is the correct way to handle credential compromise — don't ask users to delete and recreate the app, just rotate the credential.

### DELETE /apps/:id — Deactivate an application
Sets `isActive: false`. The app's existing log entries are preserved (you cannot delete audit logs — trigger prevents it). Future ingestion requests with the app's API key return 401.

## Alerting Service — Brevo Implementation

```typescript
// src/services/alertService.ts

import logger from '../config/logger';

const BREVO_API_KEY = process.env.BREVO_API_KEY!;
const ALERT_FROM = process.env.ALERT_EMAIL_FROM!;
const ALERT_TO = process.env.ALERT_EMAIL_TO!;

interface AlertPayload {
  subject: string;
  htmlContent: string;
}

async function sendAlert(payload: AlertPayload): Promise<void> {
  try {
    const response = await fetch('https://api.brevo.com/v3/smtp/email', {
      method: 'POST',
      headers: {
        'api-key': BREVO_API_KEY,
        'Content-Type': 'application/json',
      },
      body: JSON.stringify({
        sender: { email: ALERT_FROM, name: 'Audit Log Service' },
        to: [{ email: ALERT_TO }],
        subject: payload.subject,
        htmlContent: payload.htmlContent,
      }),
    });

    if (!response.ok) {
      logger.error({ message: 'Brevo alert failed', status: response.status });
    }
  } catch (err) {
    // Never throw from alertService — alert failure must not break the main flow
    logger.error({ message: 'Alert service error', error: err });
  }
}

export async function sendTamperAlert(appId: string, appName: string, sequenceNumber: number): Promise<void> {
  await sendAlert({
    subject: `[CRITICAL] Chain tampering detected — ${appName}`,
    htmlContent: `
      <h2>Chain Integrity Violation Detected</h2>
      <p>A chain verification check for app <strong>${appName}</strong> (${appId}) has failed.</p>
      <p>Tampering detected at sequence number: <strong>${sequenceNumber}</strong></p>
      <p>All entries from this sequence number onwards have invalid hashes.</p>
      <p>Immediate investigation is required.</p>
    `,
  });
}

export async function sendAnomalyAlert(appId: string, appName: string, anomaly: string): Promise<void> {
  await sendAlert({
    subject: `[WARNING] Anomaly detected — ${appName}`,
    htmlContent: `
      <h2>Unusual Activity Detected</h2>
      <p>App: <strong>${appName}</strong> (${appId})</p>
      <p>Anomaly: ${anomaly}</p>
    `,
  });
}
```

## Activity Cache — Fallback to PostgreSQL When Redis Is Down

This was mentioned in the interview Q&A section but the implementation was missing.

```typescript
// Update to src/services/activityCache.ts — add fallback

import redis from '../config/redis';
import prisma from '../config/db';
import { ActivityEntry } from '../types';
import logger from '../config/logger';

export async function getActivityFeed(
  appId: string,
  resourceId: string,
  limit: number = 20
): Promise<{ entries: ActivityEntry[]; source: 'cache' | 'database' }> {
  // Try Redis first
  try {
    const key = `activity:${appId}:${resourceId}`;
    const members = await redis.zrevrange(key, 0, limit - 1);

    if (members.length > 0) {
      return {
        entries: members.map(m => JSON.parse(m) as ActivityEntry),
        source: 'cache',
      };
    }
  } catch (err) {
    // Redis is down — log and fall through to database
    logger.warn({ message: 'Redis unavailable for activity cache — falling back to PostgreSQL', error: err });
  }

  // Fallback: query PostgreSQL directly
  const logs = await prisma.auditLog.findMany({
    where: { appId, resourceId },
    orderBy: { createdAt: 'desc' },
    take: limit,
    select: {
      id: true,
      actorId: true,
      actorType: true,
      action: true,
      resourceId: true,
      resourceType: true,
      metadata: true,
      createdAt: true,
    },
  });

  const entries: ActivityEntry[] = logs.map(log => ({
    id: log.id,
    actorId: log.actorId,
    actorType: log.actorType,
    action: log.action,
    resourceId: log.resourceId,
    resourceType: log.resourceType,
    metadata: log.metadata as Record<string, unknown> | null,
    createdAt: log.createdAt.toISOString(),
  }));

  return { entries, source: 'database' };
}
```

### Critical Database Constraint — Append-Only Trigger

This trigger is NOT in the Prisma schema. It is applied via a raw SQL migration file.

After running `prisma migrate`, create a new migration manually:

```sql
-- prisma/migrations/TIMESTAMP_add_immutability_trigger/migration.sql

-- Function that rejects any modification to audit_logs
CREATE OR REPLACE FUNCTION prevent_audit_log_modification()
RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'audit_logs table is append-only. UPDATE and DELETE operations are not permitted. Entry ID: %', OLD.id;
END;
$$ LANGUAGE plpgsql;

-- Trigger fires BEFORE any UPDATE or DELETE on audit_logs
-- FOR EACH ROW means it fires once per affected row
CREATE TRIGGER audit_log_immutable
  BEFORE UPDATE OR DELETE ON audit_logs
  FOR EACH ROW
  EXECUTE FUNCTION prevent_audit_log_modification();
```

**Why this matters:** Application-level guards (checking before calling Prisma delete) can be bypassed by bugs, compromised accounts, or direct database access. This trigger cannot be bypassed — it fires at the PostgreSQL engine level regardless of how the modification attempt arrives.

**Interview question you must be able to answer:** "Why use a trigger instead of just checking in your service before deleting?"  
**Answer:** Application code can be buggy, accounts can be compromised, and anyone with database credentials can run raw SQL directly. The trigger is enforced by the database engine itself — no code path, no SQL query, no database client can bypass it. It's immutability at the infrastructure level, not the application level.

## Core Logic — Hash Chain Service

This is the most critical file in the project. Every line must be understood.

```typescript
// src/services/hashChain.ts

import { createHmac, timingSafeEqual } from 'crypto';
import { HashPayload, VerificationResult } from '../types';
import prisma from '../config/db';

const HASH_SECRET = process.env.HASH_SECRET!;
const GENESIS_HASH = process.env.GENESIS_HASH!;

/**
 * Computes the HMAC-SHA256 hash for a single audit log entry.
 *
 * The hash is computed over a canonical JSON string of the payload.
 * Field order in HashPayload is fixed — never reorder fields.
 * The previousHash ties this entry to the previous one, creating the chain.
 *
 * @param previousHash - The hash of the previous entry (or GENESIS_HASH for entry #1)
 * @param payload - The canonical data fields of this entry
 * @returns Hex-encoded HMAC-SHA256 hash string
 */
export function computeEntryHash(previousHash: string, payload: HashPayload): string {
  const input = previousHash + JSON.stringify(payload);
  return createHmac('sha256', HASH_SECRET)
    .update(input)
    .digest('hex');
}

/**
 * Builds the HashPayload from an audit log entry.
 * The createdAt timestamp must be the one actually stored in the database.
 * Do not compute this before the row is created.
 */
export function buildHashPayload(entry: {
  appId: string;
  sequenceNumber: number;
  actorId: string;
  actorType: string;
  action: string;
  resourceId: string;
  resourceType: string;
  metadata: Record<string, unknown> | null;
  createdAt: Date;
}): HashPayload {
  return {
    appId: entry.appId,
    sequenceNumber: entry.sequenceNumber,
    actorId: entry.actorId,
    actorType: entry.actorType,
    action: entry.action,
    resourceId: entry.resourceId,
    resourceType: entry.resourceType,
    metadata: entry.metadata,
    createdAt: entry.createdAt.toISOString(),
  };
}

/**
 * Gets the hash of the most recent entry for an app.
 * Used when creating a new entry — the new entry's previousHash must equal this.
 * Returns GENESIS_HASH if this is the first entry for the app.
 *
 * IMPORTANT: This query must be wrapped in a transaction with the INSERT
 * to prevent race conditions where two concurrent requests both read the
 * same "latest hash" and both try to create entries with the same previousHash.
 */
export async function getLatestHashForApp(appId: string): Promise<string> {
  const latest = await prisma.auditLog.findFirst({
    where: { appId },
    orderBy: { sequenceNumber: 'desc' },
    select: { entryHash: true },
  });
  return latest?.entryHash ?? GENESIS_HASH;
}

/**
 * Gets the next sequence number for an app.
 * Returns 1 if this is the first entry.
 * Must be called inside the same transaction as getLatestHashForApp.
 */
export async function getNextSequenceNumber(appId: string): Promise<number> {
  const latest = await prisma.auditLog.findFirst({
    where: { appId },
    orderBy: { sequenceNumber: 'desc' },
    select: { sequenceNumber: true },
  });
  return (latest?.sequenceNumber ?? 0) + 1;
}

/**
 * Verifies the integrity of the entire chain for an app.
 *
 * Algorithm:
 * 1. Fetch all entries for the app in sequence order (sequenceNumber ASC)
 * 2. For each entry, recompute what the hash SHOULD be
 * 3. Compare recomputed hash to stored hash using timingSafeEqual
 * 4. If any entry's hashes don't match, the chain is broken at that point
 * 5. Return the result with the position of the first broken link if any
 *
 * timingSafeEqual is used instead of === to prevent timing attacks where
 * an attacker measures response time differences to guess correct hash bytes.
 *
 * Performance note: This scans the entire table for an app.
 * For very large chains (millions of entries), this is slow.
 * Acceptable for a portfolio project. Production systems use incremental verification.
 *
 * @param appId - The app whose chain to verify
 * @returns VerificationResult — valid or tampered with exact position
 */
export async function verifyChain(appId: string): Promise<VerificationResult> {
  const startTime = Date.now();

  const entries = await prisma.auditLog.findMany({
    where: { appId },
    orderBy: { sequenceNumber: 'asc' },
  });

  if (entries.length === 0) {
    return { valid: true, entriesChecked: 0, durationMs: Date.now() - startTime };
  }

  let previousHash = GENESIS_HASH;

  for (const entry of entries) {
    const payload = buildHashPayload({
      appId: entry.appId,
      sequenceNumber: entry.sequenceNumber,
      actorId: entry.actorId,
      actorType: entry.actorType,
      action: entry.action,
      resourceId: entry.resourceId,
      resourceType: entry.resourceType,
      metadata: entry.metadata as Record<string, unknown> | null,
      createdAt: entry.createdAt,
    });

    const expectedHash = computeEntryHash(previousHash, payload);

    // Convert both to Buffer for timingSafeEqual
    // timingSafeEqual requires both buffers to be the same length
    const expectedBuffer = Buffer.from(expectedHash, 'hex');
    const storedBuffer = Buffer.from(entry.entryHash, 'hex');

    if (expectedBuffer.length !== storedBuffer.length ||
        !timingSafeEqual(expectedBuffer, storedBuffer)) {
      return {
        valid: false,
        entriesChecked: entries.indexOf(entry) + 1,
        durationMs: Date.now() - startTime,
        tamperedAt: {
          sequenceNumber: entry.sequenceNumber,
          entryId: entry.id,
        },
      };
    }

    previousHash = entry.entryHash;
  }

  return {
    valid: true,
    entriesChecked: entries.length,
    durationMs: Date.now() - startTime,
  };
}
```

## Core Logic — Activity Cache Service

```typescript
// src/services/activityCache.ts

import redis from '../config/redis';
import { ActivityEntry } from '../types';

const MAX_ENTRIES = parseInt(process.env.ACTIVITY_CACHE_MAX_ENTRIES || '50');
const TTL_SECONDS = parseInt(process.env.ACTIVITY_CACHE_TTL_SECONDS || '3600');

/**
 * Redis key format: activity:{appId}:{resourceId}
 * Each key is a Redis sorted set where:
 * - score = Unix timestamp in milliseconds (for ordering)
 * - member = JSON-serialised ActivityEntry
 */
function getCacheKey(appId: string, resourceId: string): string {
  return `activity:${appId}:${resourceId}`;
}

/**
 * Adds a new event to the activity cache for a resource.
 * Uses a pipeline to execute all Redis commands atomically in one round trip:
 * 1. ZADD — add entry scored by timestamp
 * 2. ZREMRANGEBYRANK — trim to keep only the MAX_ENTRIES most recent
 * 3. EXPIRE — reset TTL so active resources stay hot
 */
export async function cacheActivityEntry(
  appId: string,
  entry: ActivityEntry
): Promise<void> {
  const key = getCacheKey(appId, entry.resourceId);
  const score = new Date(entry.createdAt).getTime();
  const member = JSON.stringify(entry);

  const pipeline = redis.pipeline();
  pipeline.zadd(key, score, member);
  pipeline.zremrangebyrank(key, 0, -(MAX_ENTRIES + 1)); // Keep only the MAX_ENTRIES most recent
  pipeline.expire(key, TTL_SECONDS);
  await pipeline.exec();
}

/**
 * Retrieves recent activity for a resource from Redis.
 * Returns entries in reverse chronological order (newest first).
 * Returns empty array if cache is cold (no entries for this resource).
 */
export async function getActivityFeed(
  appId: string,
  resourceId: string,
  limit: number = 20
): Promise<ActivityEntry[]> {
  const key = getCacheKey(appId, resourceId);

  // ZREVRANGE returns members in descending score order (newest first)
  const members = await redis.zrevrange(key, 0, limit - 1);

  return members.map(member => JSON.parse(member) as ActivityEntry);
}

/**
 * Clears the activity cache for a specific resource.
 * Called when a resource is explicitly deleted or its history is cleared.
 */
export async function clearActivityCache(
  appId: string,
  resourceId: string
): Promise<void> {
  const key = getCacheKey(appId, resourceId);
  await redis.del(key);
}
```

**Purpose:** Ingest a new audit log event.

**Success response — 202 Accepted:**

    "sequenceNumber": 47,
    "entryHash": "a3f9b2c1d4e5...",

**Why 202 and not 201:**
The hash chain operation is sequential — each entry depends on the previous one. Under high volume, entries may be briefly queued. 202 correctly signals "accepted and will be processed" rather than "created right now."

**Implementation logic inside the route handler:**
```
1. Validate API key → get app from DB
2. Validate request body with IngestEventSchema (Zod)
3. Begin PostgreSQL transaction
4. Get latest hash for app (inside transaction)
5. Get next sequence number (inside transaction)
6. Build HashPayload from input + sequenceNumber + createdAt (use NOW())
7. Compute entryHash = computeEntryHash(previousHash, payload)
8. INSERT into audit_logs with all fields including entryHash and previousHash
9. Commit transaction
10. Cache entry in Redis activity sorted set (outside transaction — fire and forget)
11. Return 202 with entryId, sequenceNumber, entryHash
```

**Error responses:**
- 400 — validation failed (missing fields, invalid format)
- 401 — missing or invalid API key
- 429 — rate limit exceeded
- 500 — internal error (transaction failed, chain computation error)

    where: { apiKey, isActive: true },
  });

  if (!app) {
    return res.status(401).json({ success: false, error: { message: 'Invalid API key', code: 'INVALID_API_KEY', statusCode: 401 } });
  }

  req.app = app;  // Attach app to request for use in route handlers
  next();
}

## Transaction Safety — The Race Condition Problem

**The problem:** Two requests arrive simultaneously for the same app. Both read `getLatestHashForApp()` and get the same previousHash. Both compute their entry hashes using the same previousHash. Both INSERT. Now two entries have the same `previousHash` — the chain is broken.

**The solution:** Wrap the read-and-insert in a PostgreSQL transaction with serializable isolation for the sequence-critical part:

```typescript
// Inside the POST /events route handler

const result = await prisma.$transaction(async (tx) => {
  // Both the hash read and the insert happen inside one transaction
  // PostgreSQL's transaction isolation prevents concurrent reads of the same "latest"

  const latest = await tx.auditLog.findFirst({
    where: { appId: req.app.id },
    orderBy: { sequenceNumber: 'desc' },
    select: { entryHash: true, sequenceNumber: true },
  });

  const previousHash = latest?.entryHash ?? GENESIS_HASH;
  const sequenceNumber = (latest?.sequenceNumber ?? 0) + 1;
  const createdAt = new Date();

  const payload = buildHashPayload({
    appId: req.app.id,
    sequenceNumber,
    actorId: body.actorId,
    actorType: body.actorType,
    action: body.action,
    resourceId: body.resourceId,
    resourceType: body.resourceType,
    metadata: body.metadata ?? null,
    createdAt,
  });

  const entryHash = computeEntryHash(previousHash, payload);

  return tx.auditLog.create({
    data: {
      appId: req.app.id,
      actorId: body.actorId,
      actorType: body.actorType,
      action: body.action,
      resourceId: body.resourceId,
      resourceType: body.resourceType,
      metadata: body.metadata ?? null,
      ipAddress: body.ipAddress ?? null,
      userAgent: body.userAgent ?? null,
      entryHash,
      previousHash,
      sequenceNumber,
      createdAt,
    },
  });
}, {
  isolationLevel: 'Serializable', // Prevents phantom reads — strongest isolation
});
```

**Interview question:** "What isolation level do you use and why?"  
**Answer:** Serializable. It's the strongest PostgreSQL isolation level. It prevents phantom reads — a scenario where two concurrent transactions each read the same "latest entry" because neither has committed yet. Serializable makes concurrent transactions behave as if they ran one after another. Performance cost is minimal for this use case because chain writes are sequential by nature.

## Key Interview Questions and Exact Answers

**Q: Why is the audit log tamper-proof?**  
A: Every entry's hash is computed from the previous entry's hash plus the current entry's data. If you change any field in any entry — even one character — that entry's hash changes. But the next entry's hash was computed using the old hash. So the next entry's stored hash no longer matches what it should be. Every entry after the modified one is also invalid. The verification endpoint recomputes every hash from scratch and finds the exact break point.

**Q: Why use a PostgreSQL trigger for append-only instead of checking in application code?**  
A: Application code can have bugs that accidentally call delete. A compromised service account could bypass application checks. Someone with database credentials can run raw SQL directly. A PostgreSQL trigger fires at the engine level — there is no code path, no SQL query, no database client that can bypass it. The immutability is enforced by the infrastructure, not by our code.

**Q: Why timingSafeEqual instead of === for hash comparison?**  
A: String comparison with === short-circuits at the first non-matching character. An attacker who can measure tiny differences in server response time can exploit this — they probe byte by byte, measuring which guesses take slightly longer before failing. timingSafeEqual always takes the same amount of time regardless of where the mismatch occurs. The attack surface is eliminated.

**Q: Why Redis sorted sets specifically for the activity cache?**  
A: Sorted sets are ordered by score — I use the event timestamp as the score. This means the most recent events are always at the top of the set without a separate sort. ZREVRANGE gives me the N most recent entries in one command. ZREMRANGEBYRANK lets me trim the set to a maximum size in one command. A Redis list would work for ordering but has no native trim-to-size-from-oldest operation. A hash has no ordering. The sorted set is the right Redis data structure for this exact pattern.

**Q: Why does the transaction use Serializable isolation?**  
A: The hash chain requires that each entry's previousHash is the hash of the immediately preceding entry — no gaps, no duplicates. Under concurrent writes, two requests could both read the same "latest hash" before either commits. Both compute their hashes using the same previousHash. Now we have two entries with identical previousHashes — the chain is broken. Serializable isolation makes concurrent transactions behave as if they ran sequentially, preventing this race condition.

**Q: What happens if the Redis activity cache goes down?**  
A: The service degrades gracefully. The `getActivityFeed` function falls back to a direct PostgreSQL query if Redis is unavailable. The activity feed is slower but functional. This is intentional — Redis is an optimisation layer, not a hard dependency for correctness. The health check endpoint reports Redis status separately so the issue is visible.

**Q: How would you scale this for very high event volume?**  
A: Three changes. First, make the hash chain computation asynchronous — accept the event immediately, return 202, and process the chain in a background queue. This decouples ingestion throughput from chain computation speed. Second, partition the audit_logs table by appId using PostgreSQL table partitioning — each app's chain is independent and can be queried without scanning other apps' data. Third, introduce incremental chain verification — instead of verifying the entire chain on demand, verify in the background from the last verified checkpoint and store the checkpoint. This makes verification O(new entries) instead of O(all entries).

## Common Mistakes to Avoid During Build

1. **Never change HashPayload field order** — JSON.stringify is used for the hash input. Field order changes = different hash = entire chain breaks on verification. Define the type once, never reorder.

2. **Never expose entryHash or previousHash in API responses** — These are internal chain fields. Exposing them doesn't break security but is unnecessary and creates confusion.

3. **Always use transactions for chain writes** — A non-transactional read-then-insert has a race condition window. Even at low traffic, it will eventually be hit.

4. **Test the trigger before relying on it** — After running the migration, manually run `DELETE FROM audit_logs LIMIT 1` in a database client and confirm it throws an error. If it doesn't, the trigger didn't apply.

5. **Test chain verification with actual tampering** — Don't just verify a clean chain. Use a database client to UPDATE one row's metadata and then run verification. Confirm it returns `valid: false` with the correct `sequenceNumber`. This is your demo. It must work.

6. **Use `no-store` cache on fetch calls in server components** — Audit logs are real-time. Next.js caches fetch responses by default. Add `cache: 'no-store'` to all data-fetching calls in server components.

7. **Set HASH_SECRET before the first entry is created** — If you change HASH_SECRET after entries exist, verification will fail for all existing entries. Treat this like a database encryption key — set it once, never change it.
